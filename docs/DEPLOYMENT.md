# نشر MTS CRM

التطبيق مستقل تمامًا عن WordPress وWooCommerce. لا تستخدم بيانات اتصال قاعدة بيانات المتجر.

## الاستضافة

Hostinger يتيح Node.js على خطط Business وCloud المدعومة. PostgreSQL ليست قاعدة البيانات المحلية المضمنة في هذه الخطط: استخدم PostgreSQL مُدارة خارجية باتصال TLS، أو Hostinger VPS لتشغيل PostgreSQL والخادم بنفسك.

مراجع رسمية راجعتها أثناء البناء:
- https://www.hostinger.com/support/how-to-deploy-a-nodejs-website-in-hostinger/
- https://support.hostinger.com/en/articles/1583659-is-postgresql-supported-at-hostinger

## خطوات النشر

1. أنشئ قاعدة PostgreSQL منفصلة ومستخدمًا خاصًا بها، وفعّل النسخ الاحتياطي اليومي واختبر الاستعادة. على قاعدة مُدارة استخدم عنوان الاتصال الموصى به من مزودها وTLS مع التحقق من الشهادة.
2. ارفع المشروع إلى مستودع خاص أو حزمة تطبيق Node.js في hPanel. استخدم Node.js 22 أو 24. لا ترفع `.env` أو `.local` أو بيانات الاختبار.
3. اضبط المتغيرات من `.env.example`: `NODE_ENV=production`، `DATABASE_URL`، سر `SESSION_SECRET` عشوائي بطول 32 حرفًا على الأقل، و`FRONTEND_URL` و`BACKEND_URL` كلاهما `https://crm.mts-makka.com`. يتبع المنفذ قيمة `PORT` من الاستضافة.
4. اضبط `TRUST_PROXY` وفق عدد الوكلاء الموثوقين الحقيقي أمام Node، عادة 1 خلف وكيل الاستضافة. لا تفتح منفذ Node للعامة عند الثقة بالوكيل.
5. نفّذ `npm ci` ثم `npm run build`. البناء يشمل Prisma وTypeScript وواجهة React. لا تحذف devDependencies قبل البناء أو قبل تشغيل أدوات الإدارة المعتمدة على tsx.
6. نفّذ `npm run db:migrate` مرة واحدة ضمن خطوة نشر مُتحكم بها، بعد أخذ نسخة احتياطية. لا تستخدم `prisma db push` للإنتاج.
7. لإنشاء المدير الأول فقط: اضبط `ADMIN_EMAIL` و`ADMIN_PASSWORD` (12 حرفًا أو أكثر) ونفّذ `npm run admin:create`. احذف متغير كلمة المرور بعد نجاح الأمر. السكربت لا يستبدل حسابًا قائمًا. لا تشغّل seed التجريبي في الإنتاج.
8. أمر التشغيل: `npm start`. الخادم يقدم React و`/api` من نفس النطاق لتبسيط الكوكيز والحماية من CSRF.
9. اربط النطاق الفرعي `crm.mts-makka.com` بتطبيق Node وفق تعليمات hPanel/DNS، واترك سجلات الموقع الرئيسي دون تغيير.
10. فعّل HTTPS/SSL، وأعد توجيه HTTP إلى HTTPS. الجلسات في الإنتاج تتطلب كوكيز Secure.
11. أعد تشغيل التطبيق من لوحة الاستضافة. على VPS استخدم systemd أو مدير عمليات، مع reverse proxy HTTPS؛ PostgreSQL على شبكة خاصة فقط.
12. تحقق من `/api/health` (200)، فتح الواجهة، تسجيل الدخول والخروج، إضافة عميل بالمبيعات، التقرير، رفض وصول مشتري الإعلانات إلى `/api/leads` برمز 403.
13. أنشئ حسابات الموظفين الحقيقية، واختبر تعطيل مستخدم وإبطال دخوله. استرجع نسخة احتياطية في بيئة منفصلة دوريًا.

## تشغيل محلي

`npm install` ثم `npm run db:local` في نافذة، و`npm run db:migrate` في أخرى. المساعد المحلي يشغّل PostgreSQL حقيقية على loopback وينشئ `.env` بأسرار عشوائية. ثم `npm run db:seed` و`npm run dev`.

إذا لديك PostgreSQL بالفعل، انسخ `.env.example` إلى `.env` واضبط اتصالك والأسرار، وتجاوز مساعد `db:local`.

حسابات demo: `admin@mts-makka.com`، `ahmed@mts-makka.com`، `mohamed@mts-makka.com`، `mahmoud@mts-makka.com`، `media@mts-makka.com`. كلمة المرور هي `DEMO_PASSWORD` التي تختارها محليًا أو ينشئها المساعد في `.env`، ولا توجد كلمة مرور ثابتة في الكود. البيانات التجريبية ليست بيانات عملاء حقيقيين.

## الأمان والتشغيل

- الجلسة عشوائية، مخزنة في PostgreSQL كبصمة HMAC فقط، وتنتهي بعد 8 ساعات. كل طلب يتحقق من نشاط المستخدم ودوره الحالي.
- تغييرات كلمة المرور/الدور وتعطيل الحساب تلغي الجلسات. الكوكي HttpOnly وSameSite=Strict. طلبات التعديل تتطلب Origin موثوقًا وJSON.
- حد محاولات الدخول داخل عملية Node. عند تشغيل أكثر من نسخة خادم استخدم حدًا مشتركًا في reverse proxy/WAF أو استبدل مخزن محدد المحاولات بمخزن مشترك قبل التوسع.
- لا ترسل كلمات مرور أو نسخ قاعدة البيانات بالبريد، ولا تسجل محتويات طلبات العملاء في سجلات الخادم.
- اختبارات التكامل تُشغّل على قاعدة محلية مخصصة للتطوير، ولا تُشغّل على قاعدة الإنتاج.

راجع [دليل التحديث](CAMPAIGNS-SHIPPING.md). على القاعدة الحالية نفّذ `npm run db:migrate` لتطبيق `20261017120549_campaign_shipping` بعد النسخ الاحتياطي وإيقاف التطبيق. لا تنفّذ seed أو reset. جميع متغيرات البيئة الحالية تبقى كما هي؛ لا توجد مفاتيح Meta/Google أو تكاملات خارجية مطلوبة، فالإدخال يدوي. أضف حالات الشحن الفعلية وحساب SHIPPING من الإدارة بعد الترقية.
